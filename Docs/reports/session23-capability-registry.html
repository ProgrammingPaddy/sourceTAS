The Capability Registry

The atomic-capability taxonomy for the surf solver, adopted as the canonical vocabulary: 29 physical capabilities, 22 certified reducers, 16 composition functions — with every existing certified asset mapped to its ID, the binding semantics that keep the library honest, and the phased build order.

2026-08-21 design of record: Docs/CapabilityLibrary.md organization session — no solver code changed
Turn Source surf physics into the smallest possible set of extremely fast, reusable min-max functions — then whatever full-map architecture eventually wins is mostly table lookup, sparse composition, and pathfinding.

01The three categories

A · PHYSICAL

What can physically happen?

Exact transforms, capability extrema / Pareto surfaces, and their inversions. The physics foundation — later functions become composition or inversion of these, not new optimizers.

B · REDUCTION

What provably needs no search?

Equations, table lookups, interval intersections, support-function tests. Extremely cheap. Nothing is promoted here without proof; dead-route culling lives here and nowhere else.

C · COMPOSITION

Which valid alternative is preferable?

Consumes proven A/B outputs against a stated objective. Never invents a physics score — C0/C1 carry information, C2–C5 are projections only.

02Binding library semantics

Five rules, each bought with a measured failure or a proof.

  1. LB admits, UB culls. A witnessed lower bound certifies possibility; only an exact or certified upper bound certifies impossibility. No B-row may ever hard-prune from an LB surface.
  2. No scalar-dominance assumptions. No capability may compress its internal state just because its requested output is scalar — Conjecture M was refuted at +34…+242 u/s because turn rate ∝ 1/v lets slower states out-turn-then-accelerate faster ones.
  3. Reference vs production, cross-falsifying forever. X_Ref is full-MoveTick truth; X_Fast is the partially-evaluated exact kernel with identical float semantics, gated bitwise (the wishparity pattern). Partial evaluation under a proven domain is not approximation.
  4. Tables canonicalize; witnesses stay world-frame. Frame rotation is exact in the reals, not in floats — so tables live in the canonical frame while every witness is an exact control schedule re-verified bitwise where it is used (the ReplayEdge practice).
  5. Domain stamps on every surface. Standing hull only, no duck, no jump, clean air, dwell-6 legality — stated boundaries, never silent assumptions.

04The dependency spine

Dashed = the Phase-0 kernel; amber = witnessed lower bounds standing; teal solid = certified. If the eight functions on the air and ride spines are solved efficiently, most of Registry B becomes trivial inversion and lookup.

05One object, five capabilities — the reach family

A8–A13 collapse into RN

Vertical is deterministic (A1) and the frame canonicalizes (A0), so the fixed-time reachable set RN(v₀, side₀, age₀) ⊂ (x, y, vx, vy) carries everything:

  • D* is its support function (A8)
  • V*/Ψ* are its velocity marginals (A6/A7) — a free cross-falsifier against capability 1's independent build
  • N_min is a membership scan over N (A10)
  • point / face solvers are witness queries, faces through (T, λ) slices (A11–A13)

Two exact consumption modes

On-demand per exact start (production): one forward sweep per entrance state with the A4-prod kernel, memoized on the session-19 K key. The measured 84–85% K-duplication says the memo hits constantly — this is the correct form of the batching lever (~6.3–6.7×).

Canonical sampled tables (bounds/design): RN over sampled v₀ with interval semantics — LB from witnesses, UB from certified envelopes; v₀-interpolation is a stated conjecture with a held-out falsifier.

Measured basis: the B@32 sweep held 474k lattice states over 90 ticks from one start in 2.2 s of MoveTicks — sub-second on the kernel.

06Why the A4-prod kernel is Phase 0

The engine is cheap; the generic path is not free. Partial evaluation under a proven domain — same float ops, same order, bitwise-gated — removes the world, position, gravity, hull, and trace from every clean-air transition.

09The build order

0
The unlock: A4-prod kernel + airkparity

Extract the exact cartesian air transition; bitwise gate vs MoveTick; measure the multiple. Every S-type build downstream runs on it.

1
Finish capability 1 + the reach family

Flat-lattice exact (v, ψ) band on the kernel; falsifier margins to zero; the turn-then-accelerate theorem. Then R_N with D* and the query modes A9–A13, cross-falsified against capability 1.

2
Board + boundary events

A16/A17 frozen from the clip law (near-analytic); A26/A27 formalized from the existing launch/END instruments.

3
Ride

A18-prod extraction settles the tangent-frame hypothesis by parity; then A19/A20, then the central A22 kernel with U_E and the exit suites as cross-checks.

4
The B battery

Promote B5/B6/B7 to UB-certified culls from the exact builds; B13/B14 successor-resource propagation; per-cull proof records.

5
The C layer + the end-state test

Labels, Pareto, sampled kernels, min-plus. Acceptance: ~10³ × 10³ ramp-point pairs on basictest — B-battery interval tests first, table queries for survivors. The full-map solve returns as composition + pathfinding. North star: real maps < 10 min; basictest seconds-to-sub-minute.
