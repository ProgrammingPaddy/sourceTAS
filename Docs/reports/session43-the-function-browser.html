01What the dashboard can do now

Click any function chip — in a capability row, a term entry, a detail drawer — and the function browser opens its real source: true line numbers from the file, the attached doc comment, comments set off typographically. The header of each entry shows the registry rows it implements, its calls and called by chips (walking the graph: Fn::Duck → Move::Duck's 68-line real body; CapP2P::SolveFreeN → MinDepartSpeed + SolveFixedN; MoveTick → its whole tick chain), and — for structs — every nested method. The list is searchable over names and code text, so "0.03125" finds the five functions that carry the trace epsilon.

02How it stays true

Generated, never transcribed. Tools/gen_capability_code.py parses the sources (namespaces, structs, nested methods, multi-line signatures, brace-exact bodies), computes the call graph, and splices the result between markers inside the dashboard. Rerunning it after any library edit is now a standing duty — the embedded code can never drift from the repo by more than one forgotten command, and the change log will catch that.

Scope is deliberate and stated on the page: the library headers whole; the vtable-pinned Fn:: export bodies; the Move:: engine-mirror implementations they forward to plus MoveTick itself; Air::WishInputs. The certification suites (the CmdCap* drivers in SolverLab.cpp) are run logs, not library code, and are not embedded. Helpers that sit on no registry row are listed and labeled honestly as helpers.

Verification before shipping: all 183 captures end on their own closing brace and contain their own name; every inventory chip resolves to a code entry (checked at page load, logged to the console); the search and the click-through paths were exercised in the browser. No engine or suite code was touched this session, so the certified state remains session 42's — seventeen suites green.
